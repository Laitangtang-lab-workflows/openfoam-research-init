# Four-line layering and data ledgers (detail)

> Origin: this file is the canon. It was distilled, with generic rewording, from an actual simulation project's `AGENTS.md` (directory-structure section), `数据\README.md` and `算例集合\00-算例台账.md`; work-level AGENTS files inside projects are instances of it.

## 1. Four-line layering (separating code from data)

Four lines under the research project root, each with its own job:

| Line | Directory | Rule |
|---|---|---|
| Code | `代码\` (per-research-part code in its own subdirectory, each with a complete `工况生成\` → post-processing toolchain; cross-project shared libraries live at the layer/project-group level `公共库\`) | **Pure scripts and libraries, zero data**; scripts anchor to the project root via `__file__` (never depending on the caller's cwd) |
| Data | `数据\原始\` (read-only) / `数据\衍生\` (regenerable) | Two-bucket rule, see §2 |
| Documents | `研究文档\` | The narrative archive mainline; `00-索引.html` is the **single index, fully auto-generated** (index generator: tech tree = self-laid-out SVG / health check / flow & borrowing / inventory — never hand-edit, rerun to regenerate); topic narratives live in each topic document's body |
| Cases | `算例集合\` | Frozen archive of computation inputs (see §3) |

At the top level, add附属 directories as needed: `手稿\` (manuscripts), ad-hoc analysis, tool scripts, etc.

**One-way data flow**: `raw →(code)→ derived →(written into)→ research docs / manuscripts` — outputs never feed back into inputs. Any urge to "write results back into raw data" means you need a new correction script, not a data edit.

## 2. Two data buckets

- **`原始\` (raw) — first-hand sources, read-only**: instrument exports (csv), values taken from literature/tables, first-hand text records (binary docx etc. goes to the synced drive, see §2.1). Iron rule: code may only read from it; output may only be written to `衍生\`.
- **`衍生\` (derived) — code output, regenerable**: fit results, post-processing output (statistics csv / figures), render products, bucketed per topic.
- **Decision test**: cannot be regenerated by a script → raw; can be produced by running code → derived; figures embedded in documents → live with the research documents.

Payoff of the two buckets: when switching machines or rerunning, the whole `衍生\` bucket can be deleted and rebuilt; `原始\` is always the trusted starting point; mistakes (code writing into raw data) are visible at a glance.

### 2.1 Binary split (repo ↔ synced drive)

The buckets split again by file form, in-repo versus synced drive; the derived bucket follows its raw source:

| Situation | Where raw goes | Where derived goes |
|---|---|---|
| Text-like (csv, md, tabulated values, …) | in-repo `数据\原始\` | in-repo `数据\衍生\` |
| Binary (images, video, …) | synced drive, same deep path `数据\原始\` | synced drive `数据\衍生\` |
| One derived product draws on raw from both sides | — (dual source) | in-repo `数据\衍生\` (unified in-repo) |

- The in-repo raw bucket **stores text files only, no binaries** — the repo is managed by git; text can be diffed line by line and reviewed; binaries can neither be reviewed nor stop the version store from bloating.
- The synced-drive side keeps same-named `数据\原始\` and `数据\衍生\`, jointly carrying the complete data flow of the binary end (raw and derived appear on the same side).
- Derived files bucket near their source for manageability: single-source regeneration depends only on same-side raw, so each side can be rerun or deleted independently; dual-source derived must be produced by in-repo code, and unifying it into the in-repo derived bucket keeps it versioned and referenceable by research documents.
- Boundary: this split governs binary first-hand data that will be processed by code (experimental images, video, …); simulation field-data entities belong to the case-library system (WSL / data drive / cluster, see §3) and are not moved to the synced drive.

## 3. Case archive and freeze discipline

**The case archive = frozen archive of computation inputs** (hand-written originals + solidified snapshots produced by scripts; no time-directory results).

- **Freeze before running**: before a case enters a compute environment (WSL / a server), it must first be frozen, locked and registered in this archive — **never archived after the fact**. An unfrozen run is a wasted run: nothing can prove what it was.
- **Freeze scope** (per case): `0/` (initial/boundary values), `constant/` (materials), `system/` (all dictionaries); **excluded**: time directories, logs, mesh products (`constant/polyMesh`, `extendedFeatureEdgeMesh`, `*.eMesh`) — the mesh is regenerated from system dictionaries + `surfaceFeatures`; `*.stl` is neither stored nor committed, it is deterministically regenerated by its generator script (gitignore as backstop).

### Double ledger

**`00-算例台账.md` (case ledger — a registry, one row per case):**

| Column | Content |
|---|---|
| Case | Directory name (with series grouping) |
| Origin | How it was generated and by which script (hand-written cases note the date and the template they were based on) |
| Status | not run / completed / completed but numbers voided (reason noted) |
| Runs | run ids (links to the run log) |
| Results went to | data bucket or research-document path |

**`00-运行台账.md` (run log — chronological, one row per run)**: run id + first 7 chars of the commit + machine + status — the run id is the cross-link key between the two books, and the provenance endpoint of "which computation do the numbers on this page come from".

## 4. AGENTS.md writing essentials (the AI collaboration entry point)

A project root and each sub-project carry their own `AGENTS.md`, serving as auto-injected context for AI sessions:

- **Rules and current state only** (present tense), no time-stamped notes — change history belongs to git;
- Content elements: directory-structure overview, data discipline (two buckets / freeze), tool preconditions (which canon to read first), terminology conventions, git discipline (one commit one thing, changes reviewed via diff before committing);
- Nested sub-projects each write their own along the directory chain, without repeating the parent, linked with relative paths;
- Major decisions go to a dedicated decision record (date + background + decision + consequence); AGENTS keeps only the conclusion.
